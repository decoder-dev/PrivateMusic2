## 1. Безопасность

### 1.1 Аутентификация (сильно)

`VKWebLoginView` + `VKWebAuthService` + `SessionStore`:

- WKWebView создан с `websiteDataStore = .nonPersistent()` —
  веб-сессия не оседает на диске.
- Навигация ограничена политикой `decidePolicyFor`: только `https`
  и только хосты `vk.ru` / `*.vk.ru` / `vk.com` / `*.vk.com`
  (`isAllowedVKHost`). Фишинг-редирект невозможен.
- Всплывающие окна (`createWebViewWith`) не открываются: запрос
  грузится в том же вебвью и только для разрешённых хостов.
- После обмена или отмены вызываются `clearWebData()` — удаляются
  все cookie и все записи `WKWebsiteDataStore`.
- Обмен cookie → токен идёт через **эфемерный** `URLSession`
  (`httpCookieStorage = nil`, `httpShouldSetCookies = false`,
  `urlCache = nil`), таймауты 20/45 с, ретраи только на 429/5xx
  и транзиентные `URLError`.
- Токен валидируется по длине (≥ 16 символов), `expires` корректно
  интерпретируется и как Unix-время, и как длительность.
- Пароли приложение не видит и не перехватывает; `client_secret`
  в коде нет (подтверждено и проверкой в `validate_project.py`).

### 1.2 Хранение сессии (сильно)

- `KeychainStore`: `kSecClassGenericPassword`, сервис = bundle id,
  доступность `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` —
  записи не мигрируют на другие устройства и не доступны до первой
  разблокировки.
- Запись идемпотентна (сначала `SecItemUpdate`, при
  `errSecItemNotFound` — `SecItemAdd`), ошибки `OSStatus`
  пробрасываются как типизированные.
- `logout()` удаляет и сессию, и профиль из Keychain.
- Восстановление сессии в `AppEnvironment.recoverSession()` защищено
  от гонок: проверяется `sessionRevision` и равенство базовой сессии,
  поэтому обмен, начатый для старого аккаунта, не может перезаписать
  новый логин/логаут. Повторная рекавери-задача шарится через
  `sessionRecovery.task` — нет веера параллельных обменов.

### 1.3 Сеть (сильно)

- `APIClient` — актор; эфемерная сессия, без cookie и кэша.
- Все эндпоинты — `https`; в коде нет ни одного `http://`;
  исключений ATS в `Info.plist` нет.
- Тело запроса — детерминированно отсортированная форма, значения
  через строгий percent-encoding (`alphanumerics + -._~`).
- 401/VK `error_code 5` → `APIError.unauthorized` → управляемая
  рекавери-цепочка; «неизвестный метод» (код 3) запоминается на
  сессию и не долбится повторно.
- Одинаковые read-запросы в полёте делят один ответ
  (`RequestCoalescingPolicy`): в ключ входит тело целиком, включая
  токен, поэтому ротация сессии не склеивает разные аккаунты.
  Записи (`не get*/search*`) никогда не коалесцируются.
- Ретраи: экспоненциальный бэкофф с джиттером, уважение
  `Retry-After`, лимиты 0.2–8 с; для стримов — политика
  «быстро упасть» без `waitsForConnectivity`.

### 1.4 Логи и маскирование (сильно)

- `AppLog.write()` применяет `AppLogRedaction.redact()` ко всем
  сохраняемым сообщениям **централизованно**, а не только на стороне
  вызывающих — защита «в два слоя».
- `AppLogRedaction` маскирует `access_token`, `refresh_token`,
  `token`, `remixdsid`, заголовки `Cookie:` и `Authorization: Bearer`,
  плюс поколючевое маскирование формы (`password`, `hash`, `code`,
  `session_id` и т.д.) и обрезку строки до 512 символов.
- Файловые логи включены по умолчанию только при разблокированном
  меню разработчика; экспорт — только по явному действию.

### 1.5 Находки по безопасности

## 3. Архитектура и качество кода

### Сильные стороны

- Последовательная схема «тонкие вью + политики-перечисления»:
  поведенческие решения вынесены в чистые `enum`-политики
  (`RequestRetryPolicy`, `StreamQualityPolicy`, `PlaybackPreloadPolicy`,
  `AudioInterruptionPolicy`, `MiniPlayerGesturePolicy` и десятки других),
  которые покрыты тестами независимо от вью.
- Внедрение зависимостей через `AppEnvironment` (единая точка сборки),
  сервисы за протоколами (`MusicService`).
- Современный стек: `@Observable`, акторы для изоляции (`APIClient`,
  `TrackShareService`), структурированная конкурентность,
  `@MainActor` на сторах и плеере.
- Всего 11 `@unchecked Sendable` (каждый с обоснованием), 78 `weak self` —
  захваты в замыканиях контролируются.
- В коде приложения **ноль** `try!`, `as!`, `fatalError` и `print(`;
  единственный `preconditionFailure` — fail-fast в `AppConfiguration`
  при битом `Info.plist` (приемлемо).
- Жизненный цикл плеера продуман: `PlaybackRegistrations` вынесен
  из `AudioPlayer` (deinit `@MainActor`-класса nonisolated) и в
  `deinit` снимает все наблюдатели `NotificationCenter`, таргеты
  `MPRemoteCommandCenter` и periodic time observer — мёртвый плеер
  не продолжает реагировать на события.
- `ObservationLoop` — аккуратная замена Combine-паблишерам для
  `@Observable` с корректным `isCancelled`.

## 4. Нативный C-слой (3 669 строк)

Проверены `PrivateMusicMedia.c` (MPEG-TS/PES/ISO-BMFF/VK-unmask),
`PrivateMusicDSP.c` (эквалайзер/компрессор), `PrivateMusicCore.c`.

Сильные стороны:

- Все публичные функции начинаются с проверок `NULL` и длин;
  каждый `memcpy` защищён сравнением с ёмкостью
  (`*elementary_length + copy <= elementary_capacity`,
  `*pes_length + payload_length <= pes_capacity`,
  `url_decoded > out_capacity → PM_VK_UNMASK_OVERFLOW`).
- Ограничители против деградации: `PM_ISO_WALK_LIMIT` при обходе
  ISO-боксов, порог 10 000 байт для «поиска» PES-старта, лимит 16
  типов в `pm_iso_contains_types`.
- DSP: защита от переполнения при шаге (`stride`/`frame_count`
  валидируются), локальная копия коэффициентов, клампинг выхода
  по флагу, состояние фильтров не теряется между вызовами.
- Переполнение при парсинге ключа `pm_vk_unmask` отсечено
  (`parsed_key > INT32_MAX` → ошибка), деление по модулю с
  нормализацией отрицательного остатка.

Находки: только S3 из раздела 1.5 (порядок проверки перед стековым
массивом). Динамических выделений в горячих путях нет.

## 5. Хранение и офлайн-загрузки

Сильные стороны:

- `DownloadCoordinator`: максимум 3 параллельных загрузки,
  дедупликация по `Track.id` (повторные источники ждут ту же задачу),
  `cancelAll()` + `waitUntilIdle()` перед «удалить всё» — отменённая
  загрузка не может воскресить файл после очистки.
- Манифесты пишутся атомарно через FIFO-очередь
  (`OfflineManifestWriteQueue`), плюс резервная копия
  `.backup` с полным снимком — переживают падение посреди записи.
- Квоты: лимит на трек 150 МБ, на библиотеку 5–100 ГБ, расчёт
  использования с разбивкой (ручные/автоматические/обложки/сироты).
- `OfflineDownloadsFeature` и валидаторы проверяют презентацию.

## 6. Экспорт и «Поделиться»

- `TrackShareService` (актор): эфемерная сессия с длинными таймаутами
  (120/600 с), проверка статуса, проверка `Content-Type`
  (`isAudioResponse`), ограничение размера 150 МБ.
- Временные файлы экспорта живут в `temporaryDirectory/PrivateMusicShare/<UUID>`;
  очистка `removeExportDirectory` защищена префикс-проверкой — не может
  удалить ничего вне каталога экспорта.
- HLS никогда не отдаётся как ссылка или «переименованный в MP3»
  плейлист: либо прямой MP3, либо честный экспорт в M4A через
  `HLSSegmentExporter`; DRM-потоки не обходятся. Соответствует
  заявленной политике проекта.

Находок нет.

## 8. CI/CD (`.github/workflows/ios-build.yml`)

Сильные стороны:

- `permissions: contents: read` на весь воркфлоу; `contents: write`
  только у джоба публикации релиза — принцип наименьших прав.
- `concurrency` с `cancel-in-progress` — устаревшие прогоны не жгут
  macOS-раннеры.
- Порядок: валидаторы → XcodeGen → unit-тесты → только затем
  релизный архив на `xcode-27`; ошибки компилятора публикуются
  аннотациями `::error`.
- Версия берётся единственным источником из `project.yml`
  (`MARKETING_VERSION`), рассинхронизация тега и версии ломает
  джоб с понятной ошибкой.
- Релиз в GitHub с ретраями вокруг нестабильного releases API,
  `--clobber` для обновления ассетов, артефакты с хранением 14 дней,
  два IPA (полный и без Watch) для сторонних подписывателей.
- `validate_watch_bundle.py` проверяет вложенный Watch-бандл перед
  упаковкой; `package_unsigned_ipa.sh` использует корректный
  Info-ZIP-рецепт (`-0 -y`, `Payload/`, без AppleDouble).

Находки:
